# Finding contract

Use this contract for initial research and periodic refreshes. Match the project's existing Markdown layout; a separate database or new schema is unnecessary.

## Required fields

| Field | Record |
| --- | --- |
| Stable ID | Competitor prefix and sequence, such as `RIV-001`; retain it across refreshes |
| Problem and impact | User task, obstacle and practical consequence; paraphrase without copying whole reviews |
| Evidence | Direct thread/comment URL, source type, publication/comment date or `unknown`, access status and checked date |
| Corroboration | Independent reports or `single report`; distinguish multiple commenters from independent threads and identify promotional interest |
| Current status | One of the statuses below, limited to the precise claim established |
| Verification | Exact vendor fact checked, official URL and check date, or the unresolved verification gap |
| Search intent | Candidate phrases grounded in the report; distinguish troubleshooting, configuration, evaluation and switching. Volume/difficulty stay `unknown` unless measured |
| Reply disposition | One of the dispositions below, a useful answer angle and posting availability. Preserve owner reply URLs/status |
| Product fit | `unassessed`, or an evidenced/hypothesized fit with the repository source to inspect, prerequisites and limitations |

When linking a whole thread for a specific comment, name the commenter and date if visible. Distinguish publication dates from crawl dates. A document-level checked date can apply to all entries if stated explicitly.

## Access and current status

Access is `opened`, `indexed-only` or `unavailable`. Indexed-only text can establish a research lead; explain which source body, later replies or resolution evidence could not be inspected.

| Status | Meaning |
| --- | --- |
| `reported-unverified` | A user report/request exists; current behavior has not been independently established |
| `documented-current` | Current official documentation supports the narrow product constraint; it does not verify every reported symptom |
| `historical-unverified` | Older evidence lacks current confirmation |
| `resolved` | Explicit resolution evidence exists; tracker closure alone is insufficient |
| `changed` | Later evidence supersedes or diagnoses the original claim; explain what remains uncertain |

An open issue proves the report is open, not that the diagnosis is correct. Preserve version/edition details and distinguish alleged causes from confirmed behavior.

## Replies and product fit

Reply disposition is `candidate`, `historical`, `resolved`, `hold` or `not-a-thread`. Record locked/archived/closed status when observable; otherwise write `posting availability unknown`. Recheck the thread, later replies and community rules before the owner replies. A bug report is not an invitation to advertise.

Keep the owner's posting status separate, initially `not contacted`. Do not infer a sent reply from a prepared draft.

For product fit, distinguish complete, partial and unsupported solutions. Check the actual plan, platform and prerequisites, especially where switching trackers is required. Do not promise free MCP, self-hosting, retained history, unlimited capacity or speed superiority from architecture alone. Keep unrelated pains and missing product capabilities in the register.

## Completion check

- Every finding has all fields, including explicit unknowns.
- Every claim traces to a source, an attributed report or a labeled hypothesis.
- Numerical claims have dated plan/edition context.
- Resolved findings and owner-entered reply/article links survive refreshes.
- Findings share an ID when they describe the same underlying problem.
